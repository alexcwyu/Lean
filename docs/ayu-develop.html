Design decisions

Decision Rationale Tradeoff Evidence
Configure handlers around one algorithm lifecycle. Setup/data/history/transactions/results can vary between deployment modes. Operational behavior and venue support depend on configuration and external implementations. Engine (L49)
Process prices and pending fills before strategy callbacks, then orders/results after them. Algorithm observes synchronized market/account state while newly submitted orders are progressed within the slice. Model fill timing must be understood before comparing to live asynchronous execution. AlgorithmManager (L47) / Run (L121) / ProcessSynchronousEvents (L70)

Strengths and limits

Strengths

  • Actual multi-asset subscription, portfolio/account and model-risk boundaries are integrated into the event lifecycle. QCAlgorithm (L70) / SecurityPortfolioManager (L35) / TrailingStopRiskManagementModel (L27)

Limitations

  • The disabled live CME option-chain case is an explicit user policy exception after an HTTP404; this does not establish working live option data. docs/validation.md (L16)
  • External brokerage/data credentials and complete market depth/queue realism are not established by the representative lifecycle audit. Engine (L49) / LiveTradingDataFeed (L41) / BacktestingBrokerage (L38)

Validation scope

The linked validation and command records preserve actual historical runs and user-authorized exclusions. This source/document review does not rerun application tests, establish live trading readiness or rank benchmark performance. Current data, credential and runtime prerequisites remain material.
